# F0 benchmark — storage, ingest and RPC

**Date:** 2026-11-01 · **Status:** measured on one host only

## Host

| Item | Value |
|---|---|
| OS | Debian 13 (trixie), kernel 6.12 |
| CPU | 8 vCPU (VMware VM) |
| RAM | 7.7 GiB |
| Disk | 50 GB **rotational** (HDD), ext4, 12 GB free |
| Bitcoin Core | v32.1.0 (regtest) |
| Build | dev profile (`opt-level=1`, `debug=1`), RocksDB 10.4.2 static, LZ4 |

These numbers are **not** a mainnet capacity claim. The disk is rotational and
the machine is small; use them only to compare changes on the same host.

## Synthetic corpus (oracle differential)

Command: `cargo test -p el-index oracle_parity_100k -- --nocapture`

| Metric | Value |
|---|---|
| Blocks | 1 200 |
| Transaction occurrences | 107 590 |
| Distinct scripts | 500 (repeated) |
| Script types | P2PKH, P2SH, P2WPKH, P2WSH, Taproot, OP_RETURN, empty |
| Wall time (generate + index + oracle + compare) | **7.2 s** |
| Index on disk after `flush_all` | **48.9 MB** |
| `txids.dat` (32 B × 107 590) | 3.4 MB |
| Approx. bytes per occurrence | ~455 B |

The corpus is UTXO-heavy (a new output is created for almost every
transaction), so bytes/occurrence is higher than a real chain of the same height.
Compaction had not been run; only memtables were flushed. Do **not** multiply this
by mainnet transaction counts.

## Regtest ingest

`e-lite index --no-follow --batch 64` over 1 000 blocks (1 coinbase tx each):

| Metric | Before RPC fix | After RPC fix |
|---|---|---|
| Wall time | 104.6 s | **3.5 s** |
| Blocks/s | ~9.6 | **~284** |
| RPC round trip | 51.6 ms | **~1.1 ms** |
| Restart with nothing to do | — | 0.15 s |

The 50× difference came from reading the HTTP response with `Content-Length`
instead of waiting for Core to close the connection (`docs/ADR-015-INGEST.md`).

## What is not measured yet
