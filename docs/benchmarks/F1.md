# F1 benchmark — bulk `blk*.dat` ingest

**Date:** 2026-11-02 · **Status:** measured on the F0 host only

This benchmark complements `F0.md` and measures the new bulk block source. It is
**not** a mainnet capacity claim: the corpus uses regtest blocks with one
coinbase transaction each, so transaction/UTXO pressure is absent.

## Host

Same as F0: Debian 13, 8 vCPU, 7.7 GiB RAM, 41 GB root filesystem, Core 32.1.0.
Debug profile (`opt-level = 1`), Core regtest with default block files.

## Bulk file format probe

Core 32.1.0, fresh regtest datadir:

- `blocks/xor.dat` exists and is **8 bytes** (`-blocksxor` default 1).
- `blk00000.dat` is preallocated to 16 MiB while holding 3 blocks.
- The whole file is XORed with the key, repeating, aligned to the **absolute
  file offset** (record 1 starts at offset 293; decoding it with key offset 0
  produces the wrong magic).
- A zero key (old blocksdir or `-blocksxor=0`) is a no-op.

## Regtest ingest, bulk source

`e-lite index --no-follow --block-source files --batch 256` over **20 000**
blocks (one transaction each):

| Metric | Value |
|---|---|
| Continuous run | **0.91 s** (~22 000 blocks/s) |
| Fetch pipeline | `readers` (parallel `pread`/RPC), ordered writer |
| Undo | written only for the reorg window (+64 safety blocks) |
| Crash test | `SIGKILL` at 0.35 s, then restart to completion |
| Digest, continuous | `a26918f6ab59b9c306538702c0eb2324773278a3698ad17966d679cd699d9403` |
| Digest, killed + restarted | same |
| Parity | **OK** |

The 0.35 s kill happened mid-index; the restart reused the locator sidecar and
the group commit, and produced exactly the same canonical digest.

## A/B parity, RPC vs files

2 000 regtest blocks (so the undo window is active), same Core, two data
directories:

| Source | Canonical digest |
|---|---|
| `--block-source rpc` | `2dbc7adf4fffad85565e7b544e1e21a772361734afe47e9c8d31a382aef98161` |
| `--block-source files` | `2dbc7adf4fffad85565e7b544e1e21a772361734afe47e9c8d31a382aef98161` |

The RPC path now also batches `getblockhash` and uses the same `apply_block`
prefetch/merkle path, so the comparison isolates the block source.

## Existing E2E with bulk enabled

- `tests/e2e_regtest.sh`: 101 blocks, full Electrum/Sparrow sequence, reorg,
  rawtx cache, snapshots. Bulk progress lines: ~20 000 blocks/s for the tiny
  regtest blocks. Passed.
- `tests/e2e_pruned_ibd.sh`: 2 000 blocks with `-prune=1 -fastprune`, supervisor
  pruned to height 1 530, history query still returned 2 000 entries. Passed.

## What is not measured

- Mainnet block sizes, UTXO random reads, RocksDB compaction and disk
  throughput during a real IBD.
- Peak RSS for a 1M-entry locator (estimated ~100 MB).
- Throughput on HDD vs SSD for the scanner tail and the `pread` readers.
- A real `-prune=550` IBD race; only the lag guard logic and the pruned-IBD E2E
  were exercised.
- The undo-skip edge case where a catch-up call is interrupted far before its
  planned target (the reorg window of the interrupted tip is weakened). Normal
  runs and SIGKILL/restart produce the same digest.

Use these numbers to compare changes on the same host, not as a hardware
requirement.
